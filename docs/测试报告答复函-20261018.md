## 二、逐项答复（B 类）

### B01 capture_stop 首调失败 reason:null —— ✅ 已修复，需重测
根因链三段全修：
1. **drain 无总时限**（卡 10s 的直接原因）：收包线程 drain 段加 2 秒上限，超时放弃残余并记录帧数（capture.py）。高流量下停止应在 **5 秒内**返回。
2. **失败不收尾**：停止超时路径现在也会 flush/close 文件（不再永久截断，见 B06）。
3. **reason:null**：capture_stop 返回值从裸布尔改为结构化 JSON（`stopped`/`exitcode`/`pcap_complete`/`warning`/`note`/`error`），桥侧按字段判定，失败必有可读 reason。
**重测**：高流量环境 start→立即 stop：期望 ≤5s 返回且 reason 有值；随后 capinfos 校验文件完整。

### B02 capture_stop 任意路径"假成功" —— ✅ 已修复（语义明示），需重测
未在抓的路径现在返回 `{"stopped": false, "note": "no active capture for path"}`——幂等行为保留但**语义自明**，不再返回裸 true。
**重测**：对从未启动的路径 stop，确认返回 `stopped:false` + note（这不是错误，是幂等明示）。

### B03 重试的 true 掩盖上一轮 pcap 损坏 —— ✅ 已修复，需重测
新增 stop 结果留存表：重复 stop 同一路径会**回放上一轮真实结果**（含 exitcode 与 `pcap_complete:false`），不再被幂等 true 覆盖。
**重测**：复现 B01 场景后重试 stop，确认仍能看到上轮 exitcode 与完整性标记。

### B04 capture_start 失败 + CAPTURE 僵尸锁 —— ✅ 已修复，需重测
桥层 `_run_batch` 语义改为：**CAPTURE 锁仅在本任务成功时保留**（等 stop 释放）；本次失败（返回 False / 异常 / 池失败）立即释放锁。同时失败响应带 reason（联动 B23）。
**重测**：start 到不存在目录 → 返回 `ok:0` + 失败原因；随后 cmd_exec 等其他工具立即恢复可用。

### B05 抓包时间戳 = 主机 uptime —— ✅ 已修复，需重测
时间戳兜底从 `time.monotonic_ns()`（开机秒数，按 Unix 纪元解释即 1970）改为 `time.time_ns()`（墙钟），并补降级告警日志。排序机制不受影响（排序键含收包序号，稳定性保持）。
**重测**：抓 10 包 → capinfos First packet time 应为当前墙钟（±5s）。已知边界：hw_ts 硬件时间戳模式为何未取到 cmsg 仍在排查，但兜底已保证时间正确。

### B06 停止失败不 flush → 尾部截断 —— ✅ 已修复，需重测
两条措施：① drain 2 秒上限让线程及时退出（进正常收尾路径：flush→close→排序）；② 极端情况下停止线程仍未退出时，主流程也会**强制收尾文件**（最坏损失 1 条记录，远优于整段尾部缺失）。
**重测**：B01 场景后 tshark/capinfos 不应再有 "cut short"/"Less data"；逐记录解析 missing_tail=0。

### B07 锁冲突错误信息靶机为"?" —— ✅ 已修复（0.2.1）
锁冲突异常现在回填真实靶机地址，文案如"靶机 10.12.131.35 锁类 shell 冲突"。
**重测**：制造锁冲突，确认 target 真名出现。

### B08 socket_listen start 忽略 listen_port —— ✅ 已修复，需重测
两个变化：① 已在监听时换端口不再静默忽略，返回明确错误"已有监听运行在端口 X，请先停止(datatype 175)"；② 新增 datatype 175 停止监听（见 B10）后，**换端口的正确流程是先 stop 再 start 新端口**，已实测通过（39002→报错→stop→start 新端口成功）。
**重测**：换端口 start 确认收到明确错误；stop 后换端口 start 确认成功。

### B09 save/clean 无实例报错形态原始 —— ✅ 已修复
服务端 172/173/175 的错误统一为 JSON 文案（`{"error":"未启动监听"}`），桥层 socket_listen 的报错随之可读。
**重测**：无监听时调 save/clean，确认报错文案为中文说明而非 `b'error'`。

### B10 socket_listen 无 stop 动作 —— ✅ 已修复，需重测
新增 datatype 175 + MCP 工具 `socket_listen(action="stop")`。已实测：start→stop→端口释放（ss 无监听）→换端口 start 成功。**注意：stop 需要 1.7.1 靶机**；对未升级靶机调用会返回可解释的失败。
**重测**：start→stop→ss 确认端口释放。

### B11 boce 放通/弹窗/非法 mode 恒判 0% —— ⚠️ 非问题（原始逻辑保持）
经 git 全史核对（1.2.1 基线 vs 当前，逐字符比对）：**"放通"从最初落地起就不存在判定实现**（走入"未知模式判定失败"分支是原始设计行为）；"弹窗"自始声明"未实现，判定为失败"。封堵/重定向两个有效模式逻辑未动过一行。工具描述已补真话（mode 仅"封堵/重定向"有效），代码零改动。如业务确需"放通/弹窗"判定，请另立需求。

### B12 chromium 依赖检查堵死封堵模式 —— ⚠️ 原始逻辑保持
依赖自检在 datatype 131 分支开头、与 mode 无关——这是既有顺序，本次未改。封堵模式的 requests 路径本身不依赖浏览器，仅在靶机缺 chromium 依赖时会被前置自检拦截。**建议**：给需要封堵模式的靶机装齐依赖，或后续版本按 mode 分流（已记录待办，未列入本批）。

### B13 boce 多目标结果无 target 标注 —— ✅ 已修复
所有走批量执行的工具，results 每项统一带 `target` 字段（`{"target": ..., ...业务字段}`），boce_run/cmd_exec/capture 等全部生效。
**重测**：多 targets 调 boce_run，确认每项可对应靶机。

### B14 replay downlink 恒 0 / flow_count 口径 —— ⚠️ 非问题（设计行为）
核实 `replayer.py`：单臂回放（uplink_iface == downlink_iface 且无 VLAN 差异）时，所有包计为 uplink、不建流——**downlink/flow_count 恒 0 是单臂模式的定义行为**。测试用单臂场景得出"恒 0"属于口径误读。工具描述已写明该口径与"需方向统计请用双接口"。如确认双接口回放下 downlink 仍为 0，请提供双接口回放的测试数据，我们再排查。

### B15 socket_listen"配合回放"说法误导 —— ✅ 已修复（描述更正）
工具描述已删除该表述，改为如实说明："接收发往该端口的 TCP/UDP 流量（TCP 监听不接收无握手的裸回放流，回放对比需回放侧重建会话或用 UDP）"——与你们实测结论一致。

### B16 remove_target listener 活跃时删除成功 —— ✅ 已修复，需重测
新增监听存活登记：`socket_listen start` 成功后在注册表登记该靶机"有活跃监听"，`remove_target` 检测到即拒绝（提示先 stop）；`stop` 成功后解除，可正常删除。已实测拒绝与解除两路径。**注意**：登记仅对 1.7.1+ 靶机生效（旧靶机无 stop 能力，登记会造成永久不可删）。
**重测**：start→remove_target 应拒绝且提示 stop；stop→remove_target 成功。

### B17 pcap_flow_extract 静默空 + 大目录爆量 —— ✅ 部分修复，需重测
① 大目录：输出超 1000 条流自动截断，返回 `{"flows":[...前1000条], "total": N, "truncated": true}`；② 静默空输出（路径不存在/非目录返回空数组）是既有行为，已在工具描述明示，行为本身保留（避免对脏路径报错中断批量流程）。
**重测**：大目录确认截断标记；单文件路径确认空数组（属预期）。

### B18 cmd_exec wait=false [null] + 白名单形同虚设 —— ✅ 已修复/说明
① wait=false 现在返回 `{"target":..., "note": "wait=false 无返回值"}`，不再是 null；② 白名单：机制本身有效（`cmd_exec_whitelist` 非空即前缀拦截），测试环境为空列表所以整体跳过——**这是配置项默认值而非缺陷**，已在 config.example.yaml 补注释样例与说明；③ 大输出：stdout 超 64KB 截断并标记 `stdout_truncated: true`。
**重测**：wait=false 确认 note；如需白名单管控，在中央节点 config.yaml 配置 `cmd_exec_whitelist` 列表。

### B19 add_target 无任何校验 —— ✅ 已修复，需重测
注册前强制 TCP 探活（3 秒），不可达直接拒绝并说明；新增 `force=True` 参数允许显式注册离线靶机（保留离线预注册能力）。
**重测**：注册假主机应被拒；force=True 应成功。

### B20 capabilities 空壳 —— ✅ 说明处理
prompts/resources 空声明是 MCP 框架（FastMCP）默认行为而非本项目显式声明。评估后**保留现状**（去掉声明需绕过框架，收益低）。对严格按 capability 探测的客户端，prompts/list 返回空列表即为"无可用 prompts"，语义可解释。

### B21 35 机浏览器拨测 Browser closed unexpectedly —— ⚠️ 原始逻辑保持，建议环境排查
浏览器生命周期管理（单例复用/超时不关 page/僵尸进程）均为既有实现，本批未动。35 机 6/6 稳定失败而 158 机正常，指向机器环境差异（依赖库/内核）。建议：在 35 机手动执行 `google-chrome --headless --dump-dom about:blank` 复现依赖问题；僵尸 chrome 可用 `kill_all_chrome` 相关手段清理。如需我们专项排查 35 机环境，请另立工单。

### B23 capture_start 返回 ok:1 + results:[false] —— ✅ 已修复，需重测
桥层精确判定：agent 返回裸 `False` 时该靶机判 failed，reason="agent 返回 False（业务失败）"。capture_start 失败现在返回 `ok:0` + 失败原因（联动 B04 锁释放）。
**重测**：start 到不可写路径 → `ok:0` + reason，而非 `ok:1`。
